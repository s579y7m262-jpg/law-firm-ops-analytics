# 07 从一次性分析到日常监测

前六章都是"算一次、出结论"。这一章解决最后一段路：**让它每个工作日自己跑。**

## 1. 为什么需要这一层

月度经营报表有一个结构性缺陷：**月初必然难看**。当月数据还没长齐（收入表最后一笔认款可能停在月中，订单的成交结果还没回写），任何"当月 vs 目标"的对比都会低估。

直接看数的人不会区分"数据没长齐"和"业务真的崩了"，于是每月初都要重新解释一遍。解法有两个，缺一不可：

1. **把当月指标做校正**（§4.3），让月初的数字本身可信；
2. **让页面自己更新**，不要每天早上手工导一遍 Excel 再截屏发群。

## 2. 运行形态

```
automation/run_monitor.bat --silent      ← 计划任务调这个（也支持双击手动跑）
        │
        ├─ 探测 Python（PYTHON 环境变量 → where python → py -3）
        ├─ 校验 import pandas, openpyxl（缺依赖直接退出 2，不让它跑到一半才炸）
        └─ src/monitor/monitor_etl.py
                │
                ├─ data/raw/ 自动发现源文件 → 指纹 → （没变就跳过）
                ├─ 计算：业绩 / 约见 / 成交率(校正) / 退费率 / 信号灯
                ├─ dashboards/monitor.html      自包含快照（可直接发人）
                └─ dashboards/monitor_data.js   热更新载荷
```

页面侧：打开 HTML 后每 **2 分钟**动态加载一次 `monitor_data.js`，比对 `meta.generated_at`，变了才重绘，右下角显示"已更新 · 时间"。

> 编码坑：`run_monitor.bat` 是 **GBK + CRLF**（中文 Windows 控制台的默认代码页），不是 UTF-8。
> 用编辑器打开时请保持 GBK 保存，否则中文提示会变乱码。`.gitattributes` 已强制 `*.bat eol=crlf`。

## 3. 八个设计决策

每条都是被真实问题逼出来的，代价也一并写清楚。

### 3.1 源文件自动发现，而不是写死文件名

`data/raw/` 里 glob `订单表_20*.xlsx` / `收入表_20*.xlsx`，年份从收入表文件名推断，订单表按 `_{year}` 过滤防止混入往年；收入表取 mtime 最新的一份（**不累加**），订单表全部合并后按订单编号去重。

- 收益：把下个月的导出丢进目录就行，不用改代码。
- 验证：复制一份订单表进目录，结果完全不变（去重生效）。
- 代价：文件名必须含年份；命名不规范会静默漏读，所以 `meta.sources` 会把实际读到的文件、大小、mtime 全部回显在页面上。

### 3.2 指纹幂等：没变就不算

指纹 = 所有源文件 `(文件名, mtime, size)` 的 SHA1，落在 `build/monitor_state.json`。相同且输出存在 → 直接跳过，日志写"源文件无变化（fp=xxxx），跳过重算"。

- 为什么：计划任务一天跑 6 次，其中 5 次源文件没动，重算是纯浪费（单次约 5–6 秒，数据量大时更久）。
- 出口：`--force` / `-f` 强制重算。

### 3.3 当月指标必须校正

沿用 [04](04-methods.md) 的 HT 删失校正：用成熟月（2 月到上月）拟合成交延迟分布 F(t)，对当月未成交样本做逆概率加权，解不动点得到校正成交率。业绩与约见量则按**历史同进度曲线 ρ(N)**（第 N 天的累计占比）折算全月。

- 硬约束：**ρ < 0.55 不外推**。月初过了几天，历史曲线还在很低的位子，此时外推等于用 5% 的样本代表全月，宁可显示"未成熟"。
- 页面同时显示原始值与校正值（如"49.2%（原始 28.6%，未成熟）"），让人知道差在哪。

### 3.4 三色之外还有一盏灰灯

退费率来自手工台账，而台账经常不跟月（本项目只到 9 月）。所以 10 月的退费率不是"0%"（绿），而是 **灰灯 + "台账只到 9 月，本月未覆盖"**。

> 把"没有数据"画成绿色，是监测看板最常见的谎。灰灯必须是一等公民。

### 3.5 滞后指标用最近完整月判定

单场产出、退费率这类指标，当月分子还没长齐，拿当月判定会系统性偏低。所以页面上写"9 月完整值，万元/场"，用最近完整月。

同理，**周均值只用完整周**（排除本周 partial），健康线换算成周：70 ÷ 4.33 ≈ 16.2 场/周。

### 3.6 全年进度跟"年内时间进度"比，不跟固定阈值比

YTD 完成 92.6%、年内时间已过 82.7% → 绿。
如果拿"<96% 就红"这种固定阈值判，10 月天天红，报警很快就没人看了。

### 3.7 阈值来自归因结论，不是拍脑袋

| 灯 | 阈值 | 依据 |
|---|---|---|
| 客场约见量（主指标） | 健康 ≥80 场，<70 预警 | 与合同额 r=0.748，是唯一强相关的可控因子 |
| 约见成交率（护栏 1） | <65% | 跌了说明是"质"的问题，加大投放没用 |
| 退费率（护栏 2） | >12% | 超过需重算量价结论 |
| 单场产出（参考） | <7 万 | 客场单场产出历史区间下沿 |

阈值同时写进 `monitor_etl.py` 顶部常量和页面 `meta.thr`，改一处即可。

### 3.8 热更新用动态 `<script>`，不用 `fetch`

页面是 `file://` 打开的（双击即开），`fetch('data.js')` 会被 CORS 拦。动态插入 `<script src="monitor_data.js?_=时间戳">` 不受此限，加载后读 `window.__MON_EXT__` 比对时间戳。

- 代价：要求 HTML 与 `_data.js` 同目录，否则热更新失效（首次快照仍可看）。

## 4. 调度

```powershell
# 注册（周一至周五 × 6 个时点）
.\automation\register_task.ps1

# 换时点 / 立刻跑一次 / 删除
.\automation\register_task.ps1 -Times "10:00,17:00"
.\automation\register_task.ps1 -RunNow
.\automation\register_task.ps1 -Unregister
```

- **6 个时点** 10:00 / 10:20 / 10:40 / 11:00 / 14:00 / 17:00：上午 CRM 导出落盘时间不稳定，20 分钟一次重试，靠指纹跳过重复计算，成本几乎为零；下午两个点覆盖补录。
- `-StartWhenAvailable`：电脑关机错过时点，开机后补跑。
- `-MultipleInstances IgnoreNew`：上一次没跑完不叠加。
- `-ExecutionTimeLimit 30 分钟`：卡死自动收尸。
- 权限：当前用户 + 交互式令牌，**不需要管理员**。

## 5. 失败与降级

| 情况 | 行为 |
|---|---|
| 找不到 Python | `run_monitor.bat` 退出码 1，提示装 Python 或设 `PYTHON` |
| 解释器缺 pandas / openpyxl | 退出码 2，提示 `pip install -r requirements.txt`（不进入 ETL） |
| 模板缺失 | 仍输出 `monitor_data.js`，日志记"⚠ 模板缺失（仅输出 data.js）" |
| ETL 抛异常 | 完整 traceback 写 `build/monitor.log`，退出码 1 |

日志在 `build/monitor.log`（追加写），文件被占用时静默跳过，不影响主流程。

## 6. 验证清单

```bash
# 1. 幂等：连跑两次，第二次应打印"源文件无变化…跳过重算"
python src/monitor/monitor_etl.py
python src/monitor/monitor_etl.py

# 2. 强制：应重新计算并打印耗时
python src/monitor/monitor_etl.py --force

# 3. 灰度灯：台账只到 9 月时，10 月退费率必须是灰灯而非绿灯
# 4. 热更新：页面开着，重跑一次 --force，2 分钟内右下角出现"已更新"
```

## 7. 为什么没上 GitHub Actions

看起来更"工程"，但对这套数据不成立：Actions 的 runner 上没有 CRM 导出的 Excel，除非先把数据入库（数据库或对象存储），并解决敏感数据出域的问题。

这一层的真实约束不是算力，而是**数据出不了律所内网**。所以调度留在本机计划任务，是当下正确的选择。真要上云，前置条件是：数据脱敏入库 → 增量同步 → 云端跑同一套 ETL。

## 8. 与主看板的关系

同一套口径，同一个源。区别只在"什么时候算"：

| | 主看板（01） | 监测仪表盘 |
|---|---|---|
| 触发 | 手工，需要结论时 | 每工作日 6 次自动 |
| 深度 | 三层下钻、可筛选、可汇报 | 只看 6 个信号灯 + 双目标进度 |
| 当月处理 | 标注"不完整" | **校正后给出可用值** |
| 受众 | 月度复盘、对外汇报 | 销售负责人每天扫一眼 |
