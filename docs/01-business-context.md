# 01 业务背景与问题定义

## 1. 业务模式

一家区域性律所的主要获客方式是**差旅约见**：销售带着律师去客户所在地当面谈案，谈成后收取代理费。

```
投放/转介绍 → 线索入库 → 约见（客场跑客户 / 主场客户到所）
                → 签合同（合同额）
                → 分期认款（首期 / 中期 / 尾款）
                → 结案 → 退费
```

四个环节对应四张表、四套口径：

| 环节 | 事实表 | 关键字段 | 谁在关心 |
|---|---|---|---|
| 线索 | CRM 客户池导出 | 来源、广告账号、创建时间 | 市场 |
| 约见 | 订单表 | 约见时间、约见类型、差旅费 | 销售 |
| 签约 | 订单表 / 收入表 | 合同总金额、业绩金额、款项类型 | 财务、合伙人 |
| 回款/退费 | 收入表 / 提成核算台账 | 认款金额、退费金额 | 财务 |

## 2. 要解决的问题

2026 年下半年，管理层提出三个问题，但**当时没有任何一份报表能同时回答**：

1. **业绩到底掉了多少？** 财务口径 9,713 万、销售口径 1.4 亿、老板记忆里"去年翻倍"——同一个"业绩"有四种算法。
2. **为什么掉？** 是约见量少了、成交率降了、客单价塌了，还是退费变多？每种解释对应完全不同的动作（补投放 / 抓转化 / 提结构 / 控退费）。
3. **接下来会怎样、什么时候该报警？** 月度报表在月初天然不可信（当月数据没长齐），需要一个"当月就能判断"的指标。

## 3. 组织与数据边界

- **区域**：4 个战区 + 已解散区域，本仓库统一用 `A区 / B区 / C区 / D区` 代号（脱敏）。
- **小组**：约 68 个作战小组，命名如 `A区行政八组`。收入表用「小组」，订单表用「归属部门」，两套命名体系不完全互通——这是本项目最麻烦的映射问题（详见 [02](02-data-pipeline.md)）。
- **人员**：花名册 955 人，含区域、小组、在职状态；`1016` 人员表另有职级/角色，但只覆盖 137 名线谈人员，未作为组织维表主源。
- **数据条件**：无数据仓库、无 BI 账号、无 API。所有分析都从 CRM **手工导出 Excel** 开始，这决定了整条链路的形态——也决定了"列名漂移""空值当重复"这类问题会成为主要工作量。

## 4. 交付原则

1. **口径先行**：任何一个指标在写代码前，先确认定义、分子分母、时间窗口、剔除规则，并留下记录。
2. **能对账**：所有下钻表的合计必须回到总表（区域件数之和 = 1,115 件，一分不差），否则不出图。
3. **可解释**：宁可报"50% 左右，但不能确认"，也不报一个看起来很精确、但没有假设说明的数字。
4. **两个受众两套产物**：给业务看单文件 HTML（双击即开，不需要装任何东西），给复核看 Excel 底表（每张表可回溯到看板的某一块）。
